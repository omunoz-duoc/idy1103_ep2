# Medición del Rendimiento y Definición de Indicadores
## ¿Por Qué Medir es Obligatorio al Evaluar Ajustes en un BD?
Cuando aplicamos cambios en una base de datos (índices, reescritura de consultas, ajustes de parámetros), no basta con “sentir que mejoró”. La evaluación del impacto requiere una mirada **cuantitativa**: medir con indicadores y comparar resultados en condiciones equivalentes.

- Medir permite distinguir entre:
	- **Mejora real** (el sistema hace menos trabajo o usa mejor los recursos)
	- **Mejora aparente** (cambió el tiempo por caché, carga distinta o variaciones del entorno)

- Una evaluación correcta responde:
	- ¿Cuánto cambió el **tiempo de ejecución**?
	- ¿Cambió el consumo de **CPU** o las **lecturas de disco**?
	- ¿Se redujo la cantidad de **filas procesadas**?

- En administración de BD, la medición cumple dos objetivos:
	- **Validar** que el ajuste es efectivo
	- **Justificar** técnicamente la decisión (con evidencia verificable)

## ¿Qué es una Línea Base y Cómo se Define el "Antes"?
La **línea base (baseline)** es el punto de referencia inicial: el conjunto de métricas obtenidas **antes de aplicar el ajuste**. Es lo que permite una comparación objetiva “antes vs después”.


- Una buena línea base debe incluir:
	- La **consulta o carga** exacta que se medirá (mismo SQL, mismos filtros).
	- Condiciones del entorno: motor (MySQL/PostgreSQL/Oracle), local/cloud y herramienta usada.
	- Las métricas registradas (tiempo, CPU, I/O, filas procesadas).

- Recomendaciones para que sea válida:
	- Ejecutar la misma prueba **más de una vez** y registrar resultados (evitar un único valor).
	- Mantener constantes las variables: mismos datos, misma consulta, misma configuración.
	- Anotar factores que puedan influir: concurrencia, caché, tamaño del dataset.

- La línea base permite responder: “¿Cómo estaba funcionando antes de que yo interviniera?”

## ¿Qué Indicadores Debo Medir para Evaluar Impacto?
Para evaluar el impacto de un ajuste, se recomienda medir un conjunto mínimo de indicadores que describan tanto el resultado (tiempo) como el costo (recursos). Esto permite explicar por qué mejoró o empeoró.

- **Tiempo de ejecución**
	- Indicador principal de experiencia de usuario.
	- Útil, pero por sí solo no explica la causa.

- Consumo de CPU
	- Subidas suelen asociarse a joins, agregaciones, funciones y procesamiento intensivo.
	- Bajas pueden indicar que el motor hace menos cálculo o usa mejor el plan.

- **Lecturas de disco / I/O**
	- Clave para detectar scans masivos o accesos ineficientes.
	- Menos lecturas suele indicar mejor filtrado o uso de índices.

- **Cantidad de filas procesadas**
	- Si se procesan muchas filas para devolver pocas, hay ineficiencia.
	- Una optimización efectiva suele reducir filas procesadas en etapas tempranas.

- **Interpretación integrada:**
	- Tiempo ↓ + I/O ↓ → mejora sólida por reducción de lectura
	- Tiempo ↓ + CPU ↑ → mejora “compensada”: más cálculo, menos lectura (requiere análisis)
	- Tiempo ↑ + locks/waits ↑ → posible problema de concurrencia (aunque el SQL sea correcto)

## Ejemplo Aplicado: Compara "Antes y Después" Con Indicadores Básicos
```sql
SELECT id, cliente_id, total
FROM ventas
WHERE cliente_id = 1050;
```

**Escenario:** se optimiza una consulta agregando un índice en una columna usada en WHERE.

**Medición “ANTES” (línea base)**
- Tiempo promedio: **2,8 s**
- CPU: **media**
- I/O (lecturas): **alto**
- Filas procesadas: **muy alto** (examina gran parte de la tabla)

**Medición “DESPUÉS” (aplicado el índice)**
- Tiempo promedio: **0,3 s**
- CPU: **baja / media**
- I/O (lecturas): **bajo**
- Filas procesadas: **bajo** (acceso más dirigido)

**Interpretación técnica**
- La mejora se explica porque el motor ahora “va directo” a las filas del cliente en lugar de recorrer masivamente.
- La evidencia es coherente: tiempo ↓ acompañado de I/O ↓ y filas procesadas ↓ → **mejora real y justificable**.

# Herramientas de Monitoreo y Recolección de Métricas
## ¿Qué Significa "Monitorear" y para Qué Sirve al Evaluar Ajustes?
Monitorear es observar el comportamiento del motor de base de datos mediante métricas y reportes, para entender **cómo se están ejecutando las consultas** y **qué recursos se están consumiendo**. En esta unidad, el monitoreo se usa para demostrar si un ajuste (índice, optimización o parámetro) tuvo impacto real.

- Monitorear permite responder preguntas clave:
	- ¿Qué consultas están consumiendo más tiempo?
	- ¿El problema es lectura (I/O), CPU, bloqueos o exceso de filas procesadas?
	- ¿El ajuste redujo el costo de ejecución o solo cambió el tiempo “por azar”?

- La medición con herramientas aporta:
	- **Evidencia objetiva** (capturas, reportes, métricas)
	- **Reproducibilidad** (otro puede verificar el antes/después)
	- **Trazabilidad** (qué cambio se aplicó y qué efecto produjo)

- Idea clave: optimizar sin monitoreo es actuar a ciegas; con monitoreo, justificas decisiones técnicas.

## Herramientas por Motor: ¿Qué Usar y Qué Evidencia Generar?
Cada motor y herramienta permite ver el rendimiento desde una perspectiva similar: tiempo, consultas costosas, consumo de recursos y planes. La diferencia está en cómo se presenta la información y qué reporte conviene usar para documentar.

- **MySQL (MySQL Workbench — Performance Reports)**
	- Útil para observar reportes de rendimiento y comportamiento general del servidor.
	- Ideal para: capturar evidencia de consultas y/o métricas antes/después del ajuste.

- **PostgreSQL (pgAdmin)**
	- Permite ejecutar y analizar consultas, revisar planes y usar paneles/estadísticas según configuración.
	- Ideal para: documentar plan de ejecución y comparar resultados de ejecución.

- **Oracle (Performance Hub)**
	- Orientado a métricas de carga, sesiones, waits, SQL con mayor consumo y diagnóstico.
	- Ideal para: justificar impacto en CPU/esperas y mostrar mejoras en consultas relevantes.
## ¿Cómo Recolectar Evidencia Correcta?
El error más común en trabajos de rendimiento es comparar mediciones que no son equivalentes. Para evitarlo, se debe recolectar evidencia de manera consistente y documentada.


- **Qué registrar siempre (mínimo):**
	- Consulta exacta (SQL final) y el ajuste aplicado (índice/parámetro).
	- Entorno: motor, versión si aplica, local/cloud, herramienta utilizada.
	- Métricas clave: tiempo, CPU/I/O (si está disponible), filas procesadas (si aplica).
	- Plan de ejecución: EXPLAIN (idealmente antes/después).

- **Cómo asegurar comparación válida:**
	- Misma consulta, mismos filtros, mismos datos.
	- Ejecutar más de una vez y reportar promedio o rango simple.
	- Evitar cambiar varias cosas a la vez (si se cambia todo, no se sabe qué generó la mejora).

- **Cómo presentar la evidencia:**
	- Tablas comparativas y capturas claras (antes y después en el mismo bloque).
	- Incluir 1–2 líneas interpretativas: qué cambió y qué significa.
	- 
**Idea clave:** evidencia útil = medible, comparable y explicable (no solo capturas sueltas).

## Ejemplo Aplicado: Evidencia "Antes y Después" Usando una Herramienta de Monitoreo
**Evidencia “ANTES” (captura o reporte)**
- Consulta ejecutada: SELECT ... WHERE cliente_id = 1050
- Tiempo promedio: **2,8 s**
- Observación: alto consumo de lectura / muchas filas examinadas (según reporte/estadística disponible)
- EXPLAIN (antes): muestra acceso tipo scan o alto costo

**Ajuste aplicado**
- Creación de índice en columna usada en filtro (y documentado en script)

**Evidencia “DESPUÉS” (captura o reporte)**
- Misma consulta ejecutada
- Tiempo promedio: **0,3 s**
- Observación: menor lectura / menos filas procesadas
- EXPLAIN (después): muestra uso de índice y menor costo

**Cómo se redacta la interpretación técnica (2–3 líneas)**
- “La mejora se evidencia en la reducción del tiempo y del trabajo del motor. El plan cambia de lectura masiva a acceso por índice, disminuyendo filas procesadas y lecturas, lo que justifica técnicamente el impacto del ajuste.”

**Idea clave del ejemplo:** el monitoreo entrega la evidencia; la interpretación conecta evidencia → causa → mejora.

# Análisis Comparativo y Justificación Técnica del Impacto
## ¿Cómo Optimizar Consultas Complejas con Índices (JOIN, GROUP BY, ORDER BY)?
En rendimiento, una mejora real no se demuestra solo con “bajó el tiempo”. Se demuestra cuando, además del tiempo, hay evidencia de que el motor hace **menos trabajo** o utiliza mejor los recursos. Por eso, la comparación debe incluir métricas y una interpretación técnica.

- Una mejora **real** suele verse como:
	- **Tiempo de ejecución ↓** y, en paralelo, **I/O ↓** o **filas procesadas ↓**.
	- Cambios en el plan (EXPLAIN) que indiquen mejor estrategia: uso de índice, menos sort, joins más eficientes.


- Una mejora **aparente** ocurre cuando:
	- Solo baja el tiempo, pero no hay cambio en filas/I/O/CPU (posible caché o variación del entorno).
	- Se midió con condiciones diferentes (otra carga, otros datos, distinta configuración).

- Recomendación para justificar:
	- Medir en condiciones equivalentes, repetir pruebas y comparar en un formato claro (tabla/gráfico).

**Idea clave:** “mejoró” significa que hay evidencia en tiempo + recursos + plan, no solo un número aislado.

## ¿Cómo Construir una Tabla Comparativa "Antes y Después"?
La tabla comparativa es el formato más claro y evaluable para presentar resultados. Debe permitir que un lector entienda rápidamente qué se midió, qué se cambió y cuál fue el impacto.


- Elementos mínimos de una tabla comparativa:
	- **Consulta** (ID o nombre: Consulta 1, Consulta 2)
	- **Ajuste aplicado** (índice, optimización SQL, parámetro)
	- **Antes:** tiempo, CPU/I/O (si disponible), filas procesadas
	- **Después:** mismas métricas
	- **Diferencia:** variación absoluta y/o porcentaje

- Buenas prácticas:
	- Usar las mismas unidades (ms o s) y mantener consistencia.
	- Incluir una fila “Interpretación” breve: 1–2 líneas que expliquen el cambio
	- No mezclar cambios: si cambias índice + consulta + parámetro al mismo tiempo, la tabla no permite atribuir el impacto.

**Idea clave:** la tabla debe permitir ver el impacto en un vistazo y sostener tu justificación técnica.


## ¿Qué Gráficos Sirven y Cómo Interpretarlos Técnicamente?
Los gráficos ayudan a evidenciar mejoras de forma visual, especialmente cuando se comparan varios indicadores o múltiples consultas. Deben ser simples y directamente conectados a las métricas del análisis.


- Gráficos recomendados (simples y efectivos):
	- **Barras “Antes vs Después”** para tiempo de ejecución por consulta.
	- Barras para **filas procesadas** o **lecturas (I/O)** si están disponibles.
	- Si hay más de una ejecución: promedio con mínimo/máximo (opcional).

- Cómo interpretar gráficamente:
- Si baja el tiempo, pero no baja filas/I/O, se debe explicar la razón probable (caché, condiciones distintas, variabilidad).
- Si bajan tiempo + filas/I/O, la mejora es más sólida y defendible.

- Conclusión técnica (lo que se espera en el informe):
	- No solo mostrar el gráfico, sino escribir 2–3 líneas que expliquen:
		- qué cambió,
		- por qué cambió,
		- qué implica a nivel de rendimiento y/o trade-offs (por ejemplo, costo en escrituras por índices).

**Idea clave:** el gráfico evidencia el cambio; la interpretación técnica explica la causa y sus implicancias.

## Ejemplo Aplicado: Tabla + Conclusión Técnica con "Antes y Después"

Tabla Comparativa (ejemplo);

| Consulta   | Ajuste Aplicado                  | Tiempo Antes | Tiempo Después | Filas Antes | Filas Después | Interpretación Técnica                                                                                                  |
| ---------- | -------------------------------- | ------------ | -------------- | ----------- | ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Consulta 1 | Indice B-Tree en cliente_id      | 2,8s         | 0,3s           | 2.000.000   | 3.500         | Se reduce lectura masiva; el plan pasa a usar índice y baja drásticamente filas procesadas                              |
| Consulta 2 | Indice compuesto (estado, fecha) | 1,9s         | 0,8s           | 600.000     | 80.000        | Mejora parcial: se reduce el conjunto previo al ORDER BY, disminuyendo el costo del sort, pero aún procesa volumen alto |
**Conclusión breve (modelo de redacción):**
“Los ajustes evidencian mejoras reales al disminuir el tiempo de ejecución y el trabajo del motor, especialmente en Consulta 1 donde bajan significativamente las filas procesadas. En Consulta 2 la mejora es moderada: aunque reduce el costo previo al ordenamiento, sigue existiendo un volumen importante de datos, por lo que se recomienda revisar filtros adicionales o reescritura de consulta.”

**Idea clave del ejemplo:** una buena evaluación muestra datos (tabla/gráfico) + interpretación técnica que conecte evidencia con causa e implicancia.
