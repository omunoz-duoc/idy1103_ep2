# Administración de Bases de Datos en Ambientes Productivos
## ¿Qué Significa "Rendimiento" en una Base de Datos?

**Rendimiento** es la capacidad de una base de datos para responder **consultas y transacciones** en un tiempo adecuado, de forma **estable**, y soportando usuarios concurrentes sin degradación notable.

 - **Tiempo de respuesta (latencia):** cuánto tarda una consulta en devolver resultados. En rendimiento, no importa solo que sea “rápida”, sino que sea **consistente** (que no varíe demasiado entre ejecuciones).

- **Throughput (capacidad):** cuántas operaciones por segundo puede sostener el sistema bajo cierta carga. Una consulta puede “no verse lenta” sola, pero reducir el throughput cuando hay varios usuarios.

- **Concurrencia:** cómo se comporta la BD cuando muchos procesos consultan o modifican datos al mismo tiempo. Aquí aparecen fenómenos como **bloqueos** y **esperas**.

- El rendimiento depende de más de un factor:
	- **SQL (cómo está escrita la consulta)**
	- **Datos (tamaño, distribución, duplicidad, cardinalidad)**
	- **Índices (existencia y pertinencia)**
	- **Recursos y configuración del motor** (CPU, RAM, disco, caché, parámetros)

## ¿Qué es una Consulta Lenta y Qué Métricas la Delatan?

Una consulta es “lenta” cuando su tiempo de respuesta es alto respecto al contexto (volumen de datos, uso esperado y recursos). La lentitud puede venir de **procesar demasiado** o de **esperar demasiado**.

**Señales típicas de una consulta lenta:**

- Devuelve pocas filas, pero **revisa (examina) muchísimas** → suele indicar filtros ineficientes o ausencia de índices.
- Usa **ORDER BY / GROUP** BY sobre grandes volúmenes → provoca ordenamientos y agregaciones costosas.
- Realiza **joins** con tablas grandes sin apoyo de índices → crecen los registros intermedios y sube el costo.
- Trae demasiados datos al cliente (por ejemplo SELECT * sin necesidad) → aumenta el tiempo por red y procesamiento.

**Métricas mínimas para diagnosticar (qué mirar siempre):**

- **Tiempo total de ejecución**: el síntoma inicial.
- **Filas examinadas vs filas devueltas**: indicador directo de eficiencia.
- **I/O (lecturas)**: alto I/O suele significar scans grandes o mala estrategia de acceso.
- **CPU**: alto CPU se asocia a cálculos, joins, funciones, agregaciones.
- **Locks / waits**: si hay transacciones concurrentes, la consulta puede tardar por **esperar** a otras.

**Regla práctica rápida:**

- Mucho tiempo + muchas filas examinadas → problema de acceso a datos (scan/índice)
- Mucho tiempo + CPU alta → cálculo/join/agregación
- Mucho tiempo + poca actividad → bloqueos/esperas

## Plan de Ejecución y Cuellos de Botella: Cómo Justificar Técnicamente el Rendimiento

El **plan de ejecución** (EXPLAIN) es la evidencia técnica que muestra cómo el motor decidió ejecutar una consulta. No dice “esto está mal” por sí solo, pero permite entender qué operación está consumiendo el tiempo.

**¿Qué revela un plan de ejecución (a nivel conceptual)?**
- Cómo se accede a las tablas: **lectura completa** vs **uso de índices**.
- En qué orden se ejecutan joins y qué estrategia usa el motor.
- Dónde aparecen operaciones costosas: **sort**, **aggregate**, **filtros**, **lecturas masivas**.
- Estimaciones del optimizador (cuántas filas cree que procesará) que pueden fallar si las estadísticas están desactualizadas.

**Cuello de botella (bottleneck):**  
Es el punto que “frena” todo el proceso, donde se concentra el mayor costo/tiempo. Identificarlo es el objetivo central del análisis.

**Tipos comunes de cuellos de botella (y qué suele haber detrás):**
- **I/O-bound**: demasiada lectura de datos (scans, filtros débiles, índices inexistentes).
- **CPU-bound**: cálculos, funciones, joins y agregaciones pesadas.
- **Lock-bound**: esperas por bloqueos de otras transacciones.
- **Resultset-bound**: devolver demasiadas filas/columnas al cliente.

## Ejemplo Aplicado: "¿Por Qué esta Consulta Podría ser Lenta?"

```sql
SELECT *
FROM ventas
WHERE cliente_id = 1050
ORDER BY fecha_venta DESC;
```

**Escenario**: tenemos una tabla grande ventas (millones de registros) y queremos listar ventas de un cliente específico.

**Consulta (conceptual):**

**Qué podría estar:**

- Si ventas es muy grande y **no hay índice** en cliente_id, el motor podría:
	- **Examinar demasiadas filas** para encontrar las del cliente → aumenta I/O y tiempo.

- Si además no hay índice (o apoyo) para ORDER BY fecha_venta:
	- Puede requerir **ordenar muchas filas** antes de entregar el resultado → operación costosa.

- Si usamos SELECT *:
	- Traemos más columnas de las necesarias → más lectura y más transferencia al cliente.

**Qué evidencias buscarías para justificarlo técnicamente:**

- **Tiempo total** alto y **filas examinadas** muy superiores a las devueltas.
- En el **EXPLAIN**, señales de:
	- lectura completa/masiva de la tabla (scan)
	- operación de **sort** por ORDER BY
- Posible impacto adicional si hay concurrencia:
	- **waits/locks** si la tabla está siendo actualizada en paralelo.

# Plan de Ejecución e Interpretación con EXPLAIN
## ¿Qué es EXPLAIN y Para Qué se Usa en Rendimiento?
**EXPLAIN** es una herramienta que muestra el **plan de ejecución**: la ruta que el motor de base de datos eligió para resolver una consulta SQL. Su utilidad principal es transformar una “sensación” de lentitud en una **explicación técnica basada en evidencia**.

- **¿Qué responde EXPLAIN?**
	- ¿Cómo accede a cada tabla? (lectura completa vs acceso por índice)
	- ¿En qué orden se combinan las tablas? (joins)
	- ¿Qué operaciones extra se aplican? (ordenamientos, agrupaciones, filtros)

- **Por qué es clave para el análisis:**
	- El motor no ejecuta “como tú lo imaginas”; ejecuta según el costo estimado.
	- Dos consultas que entregan el mismo resultado pueden tener planes distintos y tiempos muy diferentes.

- **EXPLAIN en MySQL y PostgreSQL:**
	- Ambos entregan una representación del plan, pero con formatos distintos.
	- La idea es la misma: identificar el paso más costoso y justificar el rendimiento.

## ¿Cómo Leer un Plan sin Perderse? (Qué Mirar Primero)

Un plan puede verse complejo, pero si lo lees en orden y con foco, siempre responde lo mismo: **qué operación cuesta más** y **por qué**.

- **Paso 1: identifica el “punto caro” del plan**
	- Busca señales de lecturas masivas, joins pesados u ordenamientos grandes.
	- En PostgreSQL es común ver costos/filas estimadas por nodo; en MySQL aparecen tipos de acceso y filas aproximadas.

- **Paso 2: mira el tipo de acceso a tabla**
	- **Scan (lectura amplia):** suele indicar mucha lectura → posible cuello de botella en I/O.
	- **Acceso por índice**: reduce búsqueda cuando el filtro es selectivo y el índice aplica.

- **Paso 3: revisa filtros y condiciones**
	- ¿El filtro se aplica temprano o tarde?
	- Si el motor filtra tarde, puede estar cargando datos innecesarios.

- **Paso 4: revisa operaciones “extra”**
	- **ORDER BY** (sort) y **GROUP BY** (aggregate) sobre grandes conjuntos suelen encarecer.
	- Si hay joins, evalúa si se están generando muchas filas intermedias.

## Señales Típicas en EXPLAIN que Explican Lentitud (y Causas Probables)
Estas señales son patrones comunes que te ayudan a justificar técnicamente el rendimiento sin “adivinar”.

- **Lectura completa o masiva (scan)**
	- **Qué significa**: el motor recorre gran parte (o toda) la tabla.
	- **Causas probables**: falta de índice en WHERE/JOIN, filtro poco selectivo, estadísticas deficientes, comparación con tipos distintos.

- **Ordenamiento costoso (sort)**
	- **Qué significa**: la BD debe ordenar muchas filas para cumplir ORDER BY.
	- **Causas probables**: no hay índice útil para el orden, se ordena un conjunto enorme, se seleccionan demasiadas columnas/filas.

- **Join pesado (muchas filas intermedias)**
	- **Qué significa**: el join produce demasiadas combinaciones antes de filtrar.
	- **Causas probables**: joins sin índices en columnas de relación, condiciones incompletas, tablas grandes combinadas en mal orden.

- **Agregación costosa (GROUP BY / COUNT / SUM)**
	- **Qué significa**: se agrupa/contabiliza sobre grandes volúmenes.
	- **Causas probables**: falta de filtros previos, agrupación por columnas de alta cardinalidad, datos masivos.

- **Filtro que “bloquea” el índice**
	- **Qué significa**: el motor no puede aprovechar índice aunque exista.
	- **Causas probables**: funciones sobre columnas (UPPER, DATE, CAST), conversiones implícitas, expresiones complejas.

## Ejemplo Aplicado: Documentar y Explicar un EXPLAIN (2 Lecturas Típicas)
```sql
SELECT id, cliente_id, total, fecha
FROM ventas
WHERE cliente_id = 1050
ORDER BY fecha DESC;
```

**Caso A: el plan sugiere lectura masiva + sort**
- **Qué podrías ver en EXPLAIN:**
	- acceso tipo scan o muchas filas estimadas/examinadas
	- operación de ordenamiento (sort) para el ORDER BY

- **Interpretación técnica:**
	- Se están revisando demasiadas filas para encontrar el cliente → cuello de botella I/O
	- Luego se ordenan muchas filas → cuello de botella en sort.

- **Factores probables:**
	- falta de índice en cliente_id
	- falta de índice (o combinación) que apoye ORDER BY fecha DESC


Caso B: el plan sugiere acceso por índice y menor costo
- **Qué podrías ver en EXPLAIN:**
	- uso de índice para filtrar cliente_id
	- menos filas procesadas antes del ordenamiento (o incluso orden apoyado por índice)

- **Interpretación técnica:**
	- El motor reduce el conjunto temprano, procesando menos filas → mejora latencia.
	- Disminuye el costo del sort (o se evita parcialmente).

**Cómo lo documentas en el informe (formato sugerido):**
- **Consulta:** (SQL)
- **Plan (EXPLAIN):** (captura o salida)
- **Observaciones:** tipo de acceso, filas estimadas/examinadas, presencia de sort/join/aggregate
- **Explicación técnica:** señal → causa probable → impacto en tiempo de respuesta


# Administración de Accesos en Bases de Datos NoSQL
## ¿Cómo Detectar Cuellos de Botella en una Base de Datos?
Detectar cuellos de botella significa identificar qué recurso está limitando el rendimiento (por qué se demora): lectura de datos, CPU, bloqueos, o transferencia de resultados. En la práctica, el objetivo es **separar el síntoma (tarda mucho)** de la causa (qué lo provoca).

- **Cuello de botella por I/O (lecturas)**
	- La BD lee demasiadas filas/páginas.
	- Suele pasar por scans grandes, falta de índices o filtros poco selectivos.

- **Cuello de botella por CPU**
	- El motor está “calculando” demasiado: funciones, joins, agregaciones.
	- Aumenta con consultas complejas o volúmenes altos.

- **Cuello de botella por locks/esperas**
	- La consulta no está lenta por procesar, sino por **esperar** a otra transacción.
	- Frecuente en sistemas con muchas escrituras o transacciones largas.

- **Cuello de botella por resultset/red**
	- No es solo la BD: también influye cuánto devuelve (muchas filas/columnas) y cómo viaja al cliente.

## ¿Qué Herramientas me Ayudan a Detectar Consultas Lentas? (MySQL vs PostgreSQL)
Además de mirar una consulta aislada, se necesita una visión “de sistema”: **cuáles consultas son las que más impactan** el rendimiento total.

- **MySQL (enfoque típico de diagnóstico):**
	- **Performance Schema**: permite observar eventos, esperas y comportamiento de ejecución (según configuración).
	- **Herramientas de perfilado/estadísticas**: orientadas a identificar consultas con mayor tiempo o recursos.
	- En general, la meta es obtener: qué consulta, cuánto tarda, con qué frecuencia, qué espera.

- **PostgreSQL:**
	- **pg_stat_statements**: registra estadísticas agregadas por consulta (promedios, total acumulado, cantidad de llamadas).
	- Permite priorizar por: total de tiempo, tiempo promedio, frecuencia, variabilidad.

- **Complemento obligatorio:**
	- Estas herramientas te dicen **qué consultas** son problemáticas; luego usas **EXPLAIN** para explicar **por qué**.

## ¿Cómo Priorizar Mejoras? (No Todas las Consultas Lentas son Igual de Importantes)
En rendimiento, optimizar no es “arreglar todo”, sino **priorizar** lo que entrega más impacto con menor riesgo. Para eso se recomienda evaluar consultas por costo real en el sistema.

- **Criterios de priorización más usados:**
	- **Tiempo total acumulado:** consultas que, sumadas, consumen más tiempo del sistema.
	- **Tiempo promedio alto:** consultas que tardan mucho cada vez que se ejecutan.
	- **Frecuencia:** una consulta “no tan lenta” pero ejecutada miles de veces puede ser crítica.
	- **Picos/variabilidad:** consultas que a veces funcionan y a veces explotan (posibles locks o planes inestables).

- **Clasificación rápida del problema (para orientar hipótesis):**
	- Mucho tiempo + muchas filas procesadas → **I/O/índices/filtros**
	- Mucho tiempo + CPU alta → **joins/agregaciones/funciones**
	- Mucho tiempo + esperas → **locks/transacciones**
	- Mucho tiempo + demasiada salida → **exceso de datos devueltos**

- **Resultado esperado del análisis (en un informe):**
	- Qué consultas impactan más
	- Qué evidencia lo demuestra (métricas + EXPLAIN)
	- Qué factores técnicos podrían explicarlo (hipótesis fundamentada)

## Ejemplo Aplicado: Decidir Qué Consulta Optimizar Primero (Frecuencia vs Costo)
Escenario: detectas dos consultas con problemas (en un panel de estadísticas/monitoreo).

**Consulta A (muy lenta, pero poco frecuente):**
- Tiempo promedio: **8 s**
- Llamadas/día: **20**
- Tiempo total/día: 8 × 20 = **160 s** (~2,6 min)


**Consulta B (moderada, pero muy frecuente):**
- Tiempo promedio: **0,4 s**
- Llamadas/día: **2.000**
- Tiempo total/día: 0,4 × 2.000 = **800 s** (~13,3 min)

**Conclusión técnica (priorización):**
- Aunque A “se ve peor” por promedio, **B consume más tiempo total del sistema** y afecta más usuarios.
- B suele ser mejor candidata inicial si el objetivo es impacto global.

**Cómo lo justificas con el enfoque del curso:**
- **Métrica:** priorizas por **tiempo total acumulado** + frecuencia.
- **Diagnóstico:** luego aplicas **EXPLAIN** a la consulta priorizada para ubicar el cuello de botella (scan, join, sort, locks).
- **Hipótesis:** propones factores (índices, filtros, joins, ordenamientos, bloqueos) y explicas cómo afectan el rendimiento.
