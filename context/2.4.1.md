# Estrucutra de un Informe Técnico de Optimización
## ¿Para Qué Sirve un Informe Técnico de Optimización?
Un informe técnico de optimización no es solo “contar lo que hice”, sino **demostrar con evidencia** que existía un problema de rendimiento, que se aplicaron técnicas correctas y que los resultados mejoraron de forma medible. Además, permite que otra persona pueda **revisar, validar y replicar** el trabajo.

•Un buen informe permite:
	•**Trazabilidad:** dejar claro qué se cambió, cuándo y por qué.
	•**Evidencia:** respaldar conclusiones con métricas (tiempo, filas, I/O, CPU) y planes (EXPLAIN).
	•**Reproducibilidad:** que el docente/pares puedan repetir el análisis con tus scripts y pasos.
	•**Comunicación profesional:** explicar decisiones técnicas con claridad.

•Errores comunes que se deben evitar:
	•Solo describir pasos (“hice esto y esto”) sin resultados medidos.
	•No incluir línea base (no se puede comparar).
	•Evidencias sueltas sin explicación técnica.

•Idea clave: el informe **conecta datos + decisiones + resultados**, no solo procedimientos.

## ¿Cuál es la Estructura Mínima Recomendada del Informe?
La estructura debe ser simple y consistente para que el lector entienda rápidamente: **contexto → problema → medición → ajuste → comparación → conclusión**. Esta secuencia es la base de un reporte profesional de rendimiento.

1) Portada y contexto
	- Nombre estudiante, fecha, motor (MySQL/PostgreSQL), entorno (local/cloud), herramienta (Workbench/pgAdmin).

2) Descripción de la base de datos
	- Tablas relevantes, volumen aproximado (filas), propósito general (qué representa).

3) Problema de rendimiento identificado
	- Qué consulta(s) eran lentas y cuál era el impacto (tiempo alto, muchos recursos, etc.).

4) Línea base (ANTES)
	- SQL exacto + EXPLAIN + métricas (tiempo y, si aplica, filas/I/O/CPU).

5) Técnicas aplicadas
	- Índices creados, reescritura de consulta, ajustes (lo trabajado en actividades anteriores).
	- Incluir scripts y justificar el tipo de técnica elegida.

6) Resultados (DESPUÉS)
	- EXPLAIN + métricas posteriores, mismas condiciones de medición.

7) Comparación y análisis
	- Tabla antes/después + gráfico(s) simple(s) + interpretación técnica.

8) Conclusiones y recomendaciones
	- Qué mejoró, por qué mejoró y qué trade-offs existen.

## ¿Qué Evidencias Mínimas Deben Aparecer para que el Informe sea Evaluable?
La evaluación de esta actividad se basa en que el informe contenga evidencia suficiente para respaldar decisiones. No se exige “mucho texto”, pero sí información verificable y bien organizada.

- Evidencias mínimas por consulta optimizada:
	- **Consulta SQL** (exacta, pegada en el informe).
	- **EXPLAIN antes y EXPLAIN después** (captura o salida legible).
	- **Métricas antes/después:**
		- Tiempo de ejecución (idealmente 2–3 ejecuciones y promedio o rango).
		- Si está disponible: filas procesadas, lecturas/I/O, CPU o equivalente.
- **Tabla comparativa** con diferencias (y % si corresponde).
- **Gráfico simple** (barras Antes vs Después) para visualizar mejora.

- Evidencias del cambio aplicado:
	- Scripts CREATE INDEX o registro del ajuste (con nombres claros).

- Buenas prácticas de presentación:
	- Capturas con etiquetas (Consulta 1 / Antes / Después).
	- Misma unidad de tiempo (ms o s) para evitar confusión.
	- Señalar el entorno (local/cloud) y herramienta utilizada.

**Idea clave:** la evidencia debe permitir responder “¿mejoró?”, “¿cuánto?” y “¿por qué?”.

## Ejemplo Aplicado: Estructura de una Sección de Informe
**Ejemplo de cómo se vería una sección completa y evaluable dentro del informe:**

**Consulta 1 — Problema y línea base (ANTES)**
- Propósito: listar ventas de un cliente y ordenarlas por fecha.

**Evidencia antes:**
- EXPLAIN (antes): se observa lectura masiva / sort costoso.
- Tiempo promedio: 2,8 s (3 ejecuciones).

**Técnica aplicada**
- Índice implementado: índice en cliente_id (y/o compuesto si corresponde al patrón).

**Resultados (DESPUÉS)**
- EXPLAIN (después): se observa uso de índice y reducción de filas procesadas.
- Tiempo promedio: 0,3 s (3 ejecuciones).

**Ejemplo de cómo se vería una sección completa y evaluable dentro del informe:**

| Indicador       | Antes | Después | Diferencia |
| --------------- | ----- | ------- | ---------- |
| Tiempo promedio | 2,8s  | 0,3s    | -2,5s      |
**Interpretación técnica (2–3 líneas)**
“El índice permitió acceder a un subconjunto pequeño de filas, reduciendo lecturas y filas examinadas. Esto disminuyó el tiempo de respuesta y justificó el ajuste según el cambio observado en EXPLAIN y en la medición.”

**Idea clave del ejemplo:** cada sección debe cerrar con una explicación técnica breve basada en evidencia.

# Justificación Técnica Basada en Evidencia
## ¿Qué Significa "Justificar Técnicamente" una Optimización?
Justificar técnicamente no es decir “creé un índice y mejoró”, sino explicar con claridad **por qué** esa decisión era razonable y **cómo** la evidencia demuestra el impacto. En un informe técnico, la justificación debe conectar el problema con los datos y con el resultado.

- Una justificación técnica responde 3 preguntas:
	- **¿Qué problema había?** (síntoma medible: tiempo alto, I/O alto, muchas filas procesadas, sort costoso, etc.)
	- **¿Qué decisión tomé y por qué?** (técnica aplicada: índice, compuesto, reescritura, parámetro)
	- **¿Qué evidencia demuestra el impacto?** (antes vs después: EXPLAIN + métricas + tablas/gráficos)

- En otras palabras: **problema → hipótesis → acción → resultado**.

- Errores comunes al justificar:
	- Argumentar “porque sí” o “porque lo vi en un tutorial”.
	- Mostrar solo el “después” (sin línea base no hay comparación).
	- Confundir correlación con causalidad (cambió el tiempo, pero no se controlaron condiciones).

**Idea clave:** justificar es argumentar con datos verificables, no con opiniones.

## ¿Qué Evidencia Sirve para Defender una Decisión?
La evidencia se construye combinando indicadores de rendimiento con señales del plan de ejecución. Esto permite explicar si el motor hace menos trabajo y por qué el cambio impacta el tiempo.


- Evidencias típicas (y qué demuestran):
	- **Tiempo de ejecución ↓:** mejora en experiencia de respuesta (síntoma).
	- **Filas procesadas ↓:** el motor reduce el volumen de trabajo (muy relevante).
	- **Lecturas/I/O ↓:** se evita lectura masiva (índices y filtros eficientes).
	- **CPU ↓ o ↑:** puede mostrar menor/mayor cálculo (joins, funciones, agregaciones).
	- **EXPLAIN cambia:** evidencia de cambio de estrategia (scan vs índice, sort, join).

- Cómo interpretar de forma correcta:
	- Tiempo ↓ + filas/I/O ↓ → mejora sólida, fácil de defender.
	- Tiempo ↓ pero filas/I/O igual → posible efecto caché o entorno; requiere cautela.
	- Tiempo ↑ tras indexar → puede ser mala selectividad, índice no usado o costo adicional; también se justifica (explicando por qué no funcionó).

- Recomendación para defender:
	- Incluye 2–4 líneas interpretativas después de cada tabla: “Qué cambió” y “por qué eso afecta”.

**Idea clave:** la evidencia no es solo una captura; es una captura + interpretación.

## ¿Cómo Estructurar una Buena Argumentación Técnica en el Informe?
Una argumentación sólida es breve, ordenada y trazable. Si el lector sigue tu texto, debe poder llegar a la misma conclusión con tus datos.


- Estructura recomendada para justificar cada técnica:
	- **Problema detectado**
		- “La consulta tardaba 2,8 s y procesaba demasiadas filas; EXPLAIN mostraba scan y sort.”
	- **Hipótesis técnica**
		- “La lentitud se debe a falta de acceso por índice en la columna filtrada.”
	- **Acción aplicada**
		- “Se creó índice B-Tree en cliente_id (columna usada en WHERE).”
	- **Resultado medido**
		- “Tiempo bajó a 0,3 s; filas procesadas bajaron; EXPLAIN pasó a usar índice.”
	- **Implicancias / trade-offs**
		- “El índice mejora lecturas, pero puede aumentar costo en escrituras.”

- Buenas prácticas de lenguaje técnico:
	- Evitar frases vagas (“mejoró harto”) y reemplazar por datos (“redujo 89% el tiempo”).
	- Usar términos correctos: scan, índice, selectividad, sort, join, filas procesadas.

**Idea clave:** defender decisiones es demostrar coherencia entre evidencia y conclusión.

## Ejemplo Aplicado: Justificar un Índice Compuesto con Evidencia
**Escenario:** consulta frecuente con filtro doble y ordenamiento.

**Problema (ANTES)**
- Tiempo promedio: **1,9 s**
- EXPLAIN (antes): muestra lectura amplia y sort costoso.
- Observación: se procesan muchas filas antes de filtrar/ordenar.

**Hipótesis**
- “La consulta filtra por dos columnas de forma constante y luego ordena; un índice compuesto puede reducir filas procesadas y el costo previo al ORDER BY.”

**Resultados (DESPUÉS)**
- Tiempo promedio: **0,8 s**
- EXPLAIN (después): mayor uso del índice para filtrar temprano; menor conjunto a ordenar.
- Filas procesadas: disminuyen respecto a la línea base.

**Justificación técnica (modelo de redacción)**
- “Se implementó un índice compuesto porque el patrón de consulta filtra por cliente_id y estado y requiere ordenar por fecha. Tras el ajuste, el plan reduce el volumen de filas procesadas antes del ordenamiento, evidenciando menor trabajo del motor y una disminución del tiempo de ejecución. Como implicancia, se considera el costo adicional en escrituras por mantenimiento del índice.”

# Casos Típicos de Optimización y Cómo Defender la Decisión
## Escaneo Masivo y Ordenamiento Costoso
Estos dos casos aparecen constantemente en consultas lentas. La clave es reconocer el patrón en el **plan/métricas** y elegir una técnica que reduzca el trabajo del motor.

**Caso 1: Escaneo masivo (tabla completa / muchas filas procesadas)**
- **Síntomas (evidencia):**
	- Tiempo alto + **filas procesadas muy altas**.
	- Lecturas/I/O elevadas (si está disponible).
	- En EXPLAIN suele verse acceso tipo scan (lectura amplia).
- **Causas probables:**
	- Falta de índice en columnas de filtro (WHERE).
	- Filtros poco selectivos o condiciones que impiden usar índice.
- **Técnicas típicas:**
	- Crear índice en columna(s) del WHERE.
	- Evitar funciones sobre columnas filtradas (si aplica).
- **Cómo defenderlo en el informe:**
	- “El plan mostraba scan y alto volumen de filas; el índice reduce filas procesadas y lecturas, evidenciado en EXPLAIN y tiempos.”

Caso 2: Ordenamiento (ORDER BY) costoso
- **Síntomas (evidencia):**
	- Tiempo alto + sort destacado en el plan.
	- Aumenta cuando se ordenan muchas filas.
- **Técnicas típicas:**
	- Índice que apoye el orden (según patrón y motor).
	- Reducir resultset antes de ordenar (filtrar mejor, paginar).
- **Cómo defenderlo:**
	- “El cuello estaba en el sort; tras ajustar el acceso y/o índice, el conjunto a ordenar disminuye y baja el tiempo.”

**Idea clave:** el caso se defiende mostrando **cuál era el paso caro** y cómo el ajuste reduce ese costo.

## Caso Típico 3: JOIN Costoso (Relaciones sin Apoyo) y Cómo Justificar
Los JOIN se vuelven lentos cuando el motor debe comparar demasiadas filas entre tablas o construir conjuntos intermedios grandes. El enfoque es reducir filas temprano y apoyar la relación.

**Caso 3: JOIN costoso**
- **Síntomas (evidencia):**
	- Tiempo alto en consultas con JOIN.
	- El plan muestra etapas de unión con alto costo o grandes conjuntos intermedios.
- **Causas probables:**
	- Columnas de unión sin índice (por ejemplo, tablaA.id = tablaB.a_id sin soporte).
	- Filtros aplicados tarde (primero une, después filtra).
- **Técnicas típicas:**
	- Indexar claves foráneas/columnas de join.
	- Reordenar la consulta para filtrar antes (cuando sea posible y coherente).
- **Cómo defender la decisión:**
	- “El plan indicaba alto costo en la unión; al indexar columnas de relación y reducir filas previas, baja el volumen intermedio y se reduce el tiempo.”

**Idea clave:** una buena defensa explica qué unión era el cuello y cómo el índice reduce comparaciones.

## Caso Típico 4: Índice Compuesto Mal Diseñado / Sobreindexación
A veces el problema no es falta de índice, sino índices mal diseñados o demasiados índices. Este caso es clave porque demuestra criterio profesional (no todo se “soluciona” agregando índices).

Caso 4: Índice compuesto que no se usa (o se usa mal)
- **Síntomas (evidencia):**
	- Se creó un índice compuesto, pero EXPLAIN no lo utiliza o la mejora es mínima.
	- Filas procesadas no bajan de forma relevante.
- **Causas probables:**
	- Orden de columnas incorrecto (no coincide con patrón de filtros).
	- Baja selectividad en la primera columna del índice.
	- Consulta no filtra como se esperaba (o usa funciones/casts).
- **Cómo defenderlo:**
	- “Aunque se implementó un índice, el plan no lo usa (o lo usa parcialmente) por selectividad/orden; por eso la mejora no es significativa.”

Sobreindexación (cuando “optimizar” puede empeorar)
- **Síntomas:**
	- Lecturas mejoran un poco, pero escrituras empeoran o el sistema se vuelve más pesado.
- **Defensa técnica:**
	- “El índice tiene costo de mantenimiento; sin evidencia de uso frecuente o impacto real, no se justifica mantenerlo.”

**Idea clave:** defender también incluye explicar **por qué una optimización no funcionó** o por qué no conviene agregar más índices.

## Ejemplo Aplicado: "Scan + ORDER BY"
```sql
CREATE INDEX idx_ventas_cliente ON ventas(cliente_id)
```

1) **Evidencia del problema (ANTES)**
Tiempo promedio: **2,8 s**
EXPLAIN: lectura amplia (scan) + sort costoso por ORDER BY
Observación: muchas filas procesadas antes de ordenar

2) **Hipótesis**
“El cuello de botella está en leer demasiadas filas para un cliente específico, lo que genera un conjunto grande que luego se ordena.”

3) **Técnica aplicada**
Índice B-Tree en columna de filtro (imagen)

4) **Evidencia del impacto (DESPUÉS)**
Tiempo promedio: **0,3 s**
EXPLAIN: uso de índice → menos filas procesadas → menor costo previo al ORDER BY

5) **Defensa (modelo de redacción para el informe)**
“Se implementó un índice en cliente_id porque la evidencia mostraba lectura masiva en el WHERE. Tras el cambio, el plan pasó a usar índice, reduciendo significativamente filas procesadas y el tiempo total. La mejora es consistente y se respalda con EXPLAIN antes/después y la comparación de tiempos. Como trade-off, el índice añade costo de mantenimiento en escrituras.”
